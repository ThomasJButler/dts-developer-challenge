Manage your tasks Design spec
HMCTS internal tool

Design specification

A single-user task-management tool for HMCTS caseworkers, built on GOV.UK Frontend, server-rendered with Nunjucks and Express, with progressive enhancement only.

Open the interactive prototype to see these screens in their working states.

1. Overview

The service has three screens and one confirmation page:

  1. Task list at /tasks
  2. Create a task at /tasks/new
  3. Task detail at /tasks/:id, with the update-status form and the delete entry point
  4. Delete confirmation at /tasks/:id/delete (added because destructive actions need a confirmation step under WCAG 2.2 SC 3.3.4)

All forms POST to the same URL they were rendered from. The server validates, and either redirects to the next screen (303 See Other) or re-renders the form with errors. There is no client-side router, no XHR.

Why a confirmation page for delete?

A single-step delete from the detail page would meet the brief literally, but WCAG 2.2 SC 3.3.4 (Error Prevention for legal, financial, data) requires either reversibility, checking, or confirmation for actions that modify or delete user data. A separate confirmation page is the GOV.UK pattern and the lightest way to meet it. The warning button on the detail page links to the confirmation; the actual destructive POST is on that confirmation page.

Rationale

  • Table over card grid. A table scans faster for caseworkers comparing due dates and statuses across many items, which is the primary job. The table degrades to stacked, labelled blocks below 641px using a small CSS rule that hides the <thead> and shows data-label values via ::before. The semantics stay table semantics, so screen readers still announce row and column relationships.
  • Title is the link target. Following the GOV.UK pattern, the title cell is itself the link to the detail page. The explicit "View" link in the Actions column is a redundancy for users who scan to the right edge looking for an action - it carries a visually-hidden suffix with the reference so each link has a unique accessible name.
  • Reference under the title. Case-style refs (CR-2026-0142) earn their place because that is how caseworkers cite work to colleagues. They sit as small grey hint text under the title, not as their own column, to keep the row scannable.
  • Default sort. Not-done first, then by due date ascending, with no-date items last. This is the GOV.UK service-pattern default for "things I need to do". Sortable columns are explicitly out of scope.
  • Create button placement. Top-right on the same row as the heading at desktop (the GOV.UK heading-row pattern); below the heading at mobile, on its own line, so the touch target is full-width and not crowded.

Rationale

  • Date + time as one fieldset. The brief offered two routes; this is the one I recommend. The GOV.UK govukDateInput macro accepts an items array, so the same visual pattern stretches to five inputs. A single legend, single hint, single error message. Two separate fieldsets would double the assistive-tech overhead for no extra clarity. The visual distinction between date and time is achieved with a small gap, not a new fieldset.
  • Optional due date. Caseworkers have admin tasks with no real deadline. Making the field optional with "all blank or all filled" validation avoids a forced fake date.
  • Status as radios, not a select. Three options. Radios are visible, faster to operate by keyboard, and consistent with the update-status form on the detail page.
  • Preserving values on error. Every field reads from a values object provided by the controller after validation, so the user never re-types after a failure. The error summary lists errors in the same order as the form, and each summary link points at the first input id of the offending field, including #due-day for the date-time group (the date-input macro's documented anchor).
  • Page title prefix. When there are errors, the <title> is prefixed with "Error: " per the GOV.UK pattern, so screen readers and tab titles announce the failure on page load.
  • Cancel as a link. Cancel is navigation, not a destructive action, so it is a link not a button. Sits inside the govuk-button-group for spacing.

Delete this task

Deleting removes the task and its history. This cannot be undone.

{{ govukButton({ text: "Delete this task", href: "/tasks/" + task.id + "/delete", classes: "govuk-button--warning" }) }} {% endblock %}

Rationale

  • Two separate forms on one page. The update-status form posts to /tasks/:id/status and the delete entry point links to /tasks/:id/delete. Keeping them separate prevents a misclick on Save from triggering anything destructive.
  • Status form pre-selected to current value. Saving without changing the radio is a no-op for the user, but the controller still records an updated_at only if the value actually changed.
  • Summary list for read-only fields. govukSummaryList is the right component for "facts about this thing", aligns labels and values, and reads correctly as a definition list.
  • Time format. The brief calls for Europe/London display, format D MMMM YYYY, HH:mm. Both dueLabel and the audit timestamps use that format, so users never have to translate between UTC and London time.
  • Warning button. The govuk-button--warning style is reserved for actions with unrecoverable consequences. It is a link styled as a button so it can use a GET to the confirmation page (the actual destructive POST is on the next page).

7. Accessibility checklist for build

Target: WCAG 2.2 AA. The list below is a build-team checklist, not an audit. Use it during PR review.

Landmarks and document structure

  • Skip link with href="#main-content" as the first focusable element on every page.
  • One <main id="main-content"> per page. Service header is in <header role="banner">, footer in <footer role="contentinfo">.
  • Exactly one <h1> per page. Headings descend without skipping levels (h1 -> h2 -> h3).
  • <html lang="en-GB">.

Focus order and visible focus

  • Tab order on each screen follows visual reading order: skip link -> service header link -> back link -> H1 (programmatic focus only) -> form/content -> footer.
  • Use GOV.UK Frontend default focus style (3px yellow outline, 4px black underline). Do not override.
  • On every navigation to a new page, programmatic focus moves to the main heading (set tabindex="-1" on the <h1> and call focus() after page load). On a page rendered with errors, focus moves to the error summary instead.

Labels and id pairings

  • Every input has an explicit <label for>. Group inputs (radios, date-input) live inside a <fieldset> with a <legend>.
  • Hints use aria-describedby pointing at the hint's id (#title-hint, #due-hint, etc).
  • Error messages use aria-describedby alongside the hint id (space-separated), and inputs in error get aria-invalid="true" and the govuk-input--error class.
  • Inline error text is prefixed with a visually-hidden "Error:" so it announces correctly.

Error summary linking

  • Summary appears at the top of <main>. Receives focus on render.
  • List order matches field order on the page.
  • Each link's href is the id of the first focusable input in that field:
    • Title -> #title
    • Status -> #status (first radio input)
    • Due date and time -> #due-day
  • Clicking a summary link moves focus to the input and scrolls it into view. Use the GOV.UK Frontend error-summary JS module - do not write a bespoke handler.

Colour contrast

  • Body text #0b0c0c on #ffffff: 19.6:1, passes AAA.
  • Hint text #505a5f on #ffffff: 7.0:1, passes AAA.
  • Links #1d70b8 on #ffffff: 4.85:1, passes AA.
  • Tag text on tag background is set by GOV.UK Frontend defaults; do not change individual tag colours.
  • The blue header underline (10px #1d70b8) is decorative, not a content carrier - no contrast requirement.
  • Status tag colours (grey, blue, green) are never the only signal: the tag text label is always present alongside the colour.

Keyboard interaction

  • Radios: arrow keys move between options within a group and update the selection; Tab moves out of the group. This is browser-native and must not be overridden.
  • Buttons (<button type="submit">) are activated by Space or Enter. Link-styled buttons (role="button" on an <a>) get the GOV.UK Frontend module attached so Space activates them too.
  • Back link is a plain <a>; Enter follows it.
  • All interactive controls have a visible focus ring (GOV.UK Frontend default).

Responsive and zoom

  • Usable at 320px width. The task table stacks to labelled cards below 641px.
  • Page reflows correctly at 200% zoom in a 1280x1024 viewport (WCAG 1.4.10).
  • Touch targets minimum 24x24 CSS pixels (WCAG 2.5.8); GOV.UK Frontend defaults already exceed this.

Forms and state

  • novalidate on every form so the server, not the browser, owns the validation messages (consistent UK English wording).
  • Previously-entered values are preserved on validation failure. The server passes back a values object with every field.
  • Status update form and delete entry point are separate forms, so a misclick cannot trigger destructive action.

8. Out of scope

The build does not include any of the following. If a future story asks for one, treat it as a new design problem rather than a small addition.

  • Filtering tasks by status or date range.
  • Sorting by column.
  • Pagination, infinite scroll, or any list virtualisation. The single user is expected to have a small caseload at a time.
  • Search.
  • Drag-and-drop reordering or status changes.
  • Bulk actions (multi-select rows, batch delete).
  • Editing the title, description, or due date after creation. Status is the only mutable field.
  • Comments, attachments, or any rich content beyond the description text area.
  • Multi-user features: assignment, sharing, mentions, audit log of who changed what.
  • Notifications, email, or any asynchronous comms.
  • Real-time updates or websockets. The page is fully rendered on each navigation.
  • Dark mode or theme switching. The service inherits the standard GOV.UK Frontend appearance.

9. Build notes

  • Date storage: ISO 8601 UTC. Display in Europe/London via a Luxon helper, format string d LLLL yyyy, HH:mm.
  • Validation order: title -> status -> due. Error summary is built in this order.
  • CSRF: include a hidden token on every POST form. The GOV.UK Frontend macros do not add this for you.
  • POST/Redirect/GET: after a successful create or delete, redirect with 303 to the target page and use a flash message to render the success notification banner. After a status update, redirect to the same detail page with the flash. This prevents double-submit on refresh and keeps URLs shareable.
  • No PII in fixtures, ever. Example data uses fictional case references like CR-2026-0142 and impersonal task titles.
